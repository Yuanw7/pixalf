# 项目推进规则

唯一项目说明是根目录README.md；其他文档引用它，不另建冲突的目标或版本定义。当前游戏版本0.9.0，迭代014以横向木头人、腹部门和五关按钮出口为范围；历史迭代002/003保留为历史。

## 每次推进
1. 检查README、当前架构、任务卡、最近迭代及验收证据，说明本次范围。
2. 创建任务卡，记录依赖、成果入口和可观察验收行为，再实施。
3. 新需求先登记变更影响；目标改变、范围扩大、不可逆操作需要说明影响并请求用户决定。已授权范围内的实现和可逆修正自行推进。
4. 执行与改动相关的验证。截图用于画面验收，模型测试用于逻辑验证，二者分别记录。
5. 更新任务状态、架构、决策、迭代、CHANGELOG和README；记录未完成事项。
6. 交付快照、源码、启动说明和清单；验证包入口，保留上一可用版本；使用统一状态报告。

## 完成标准
任务状态只使用：待开始、进行中、待验证、已完成、阻塞。待验证表示实现已有但证据未齐；阻塞必须写明原因、尝试和可继续的工作。
标记已完成之前：实际入口可用、核心流程通过；关键错误/取消/重复操作处理有证据；受影响旧功能完成必要回归；界面/素材检查实际画面；文档与实现一致；限制已记录。
每项任务另列四项状态：代码完成、技术通过、用户认可、已交付。代码与技术通过不能代替用户认可；本地原型交付不能写成正式公开发行。无需代码的管理任务填“不适用”，并单独记录文档或工具完成情况。

## 变更和证据
变更登记在 changes.md，写明模块、数据、素材、验收和回退影响。变更获准后更新README范围与相关决策；旧决策标记被哪份新决策替代，不删除历史。
每项证据包含版本/快照、环境、步骤、预期、实际、文件位置和限制。旧证据只证明旧快照；新版本未验证的行为写“待验证”。

## 交付和恢复
执行 `npm run build` 产生新目录；已有目录不会被覆盖。控制台输出实际交付位置，以该目录为准，不把同版本其他快照混作本次交付。
核对BUILD_MANIFEST.json中的SHA256后，独立打开game/index.html执行开始、操作、结算、重开；记录平台和结果。HTTP入口通过不能代替file入口实测。
回退使用已验收旧目录，先核对旧清单，再重新打开其入口；不要覆盖工作区或删除用户存储。源码恢复先解压source.zip到新目录，按README启动并验证。
保存schema改变时先保留旧数据，验证旧版本读入、未知版本处理、损坏数据、写入失败、重复结算；失败时保留可恢复原始数据，不自动清空用户数据。
